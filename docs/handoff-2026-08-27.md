# 交接文档 — 2026-08-27 兼容性专项

> 这份文档给下一次接手的人（人或 agent）直接读。读完应该能不问任何问题就继续干活。
> 涉及**两个仓库**，动手前先确认自己在哪个仓：
> `Codex-Dream-Skin` = 桌面客户端（macOS Swift + Node / Windows PowerShell + Node），issue 与 PR 全在这里；
> `dreamskin-cc` = 网站（React/Vite + Go API），Cloudflare Pages + VPS。

## 1. 这一轮要解决的根本问题

上游 Codex Desktop 每发一版就打断一次换肤。近两个月的失效时间线：

| Codex 版本 | 破坏点 |
| --- | --- |
| 26.715.9757 → .10079 | owl runtime 把 `--remote-debugging-port` URL 编码进 `codex://` path |
| 26.721.x | 首页 `home-icon` 渐进渲染被判成注入校验失败 |
| 26.727.40816 | 主表面 / 顶栏语义类改成 CSS Modules |
| 26.803 | Owl composer 换成 `_ComposerLayoutBody_` / `_ComposerLayoutFooter_` |
| 26.814 | 输入框壳迁到 `_ComposerLayoutRoot_`，旧别名误绑到内层 footer |
| 26.818 | composer 底部白框、链接与 Mention 分色、消息透明度 |

两周内被迫连发 v1.5.13 / 14 / 15 / 16。**每次改的只是几个选择器字符串，但交付粒度是整个安装包。**
用户等不及就会自己打包——#373 里真的有人上传了第三方 `Setup-v1.5.15.zip` 让别人下载。

结论写在 `docs/compat-profile-design.md`：**兼容适配的变更频率由上游决定，不该由我们的发版节奏决定。**
那份文档是本轮唯一没有实现的东西，也是最该做的下一步。

`6c28be1` 含四件事：

1. **#218 watcher 空转**。目标发现退避上限写死 500ms，Codex 退出后每秒轮询约 2 次。**在维护者本机复现**：`injector-error.log` 4 分 22 秒 82 行 `fetch failed`。改成上限随连续失败时长升级（10s 后 5s，60s 后 30s）。空闲 10 分钟 1200 次 → 55 次。
   **刻意没有做「Codex 退出就停 watcher」**（#264 / #353 两个 draft 的方向）——那正是 #200「关闭重开后热切换失效」的成因。
2. **更新检查报错版本号**。`check-update-macos.sh` 读自身同级的 `VERSION` 判断「当前版本」，而客户端优先执行**已部署引擎**里的副本。引擎是启动后异步安装的，且只要 Codex 在运行安装就被拒绝（`Close Codex before installation…`，本机日志 90 秒内被拒 4 次）。拒绝一持续，App 已是新版、引擎还是旧版 → 客户端对着自己正在运行的版本弹「发现新版本」。改成更新检查一律优先用 App 包内副本。
3. **CI 产出 Windows Setup.exe**。此前 CI 只是编译它做构建检查然后丢掉，只有 macOS 上传 DMG——**所以以往 Windows 侧的修复根本没有可交给报告者验证的产物**。同时把 `pull_request` 的 `branches: [main]` 过滤去掉，否则叠在别的分支上的 PR 一个 check 都不跑。
4. **选择器合同 provenance 闸门**。`verifiedAgainst` 一直停在 26.727，而选择器早已覆盖到 26.818，引用它的 doctor 报告因此是误导性的。重写成逐版本 + 显式证据强度（`maintainer` / `reporter` / `fixture`）+ `gaps`，并加 `tools/check-selector-provenance.mjs` + CI 步骤：改 `selectors[]` 不动 `verifiedAgainst` 就构建失败。

`c5b3a0e`，**已 push 并已部署到 Cloudflare Pages，线上已验证**（`dreamskin.cc` 的 bundle 里是 `v1.5.16`）。

2. **加了 `.github/workflows/client-release-drift.yml`**：每天比对站点 pin 与客户端 latest release，不一致就红。

   改成四态：`pending`（立刻反馈）→ `handedOff`（提示去客户端窗口确认）→ `stalled`（疑问句，且**监听器保持挂载**，迟到的确认自动撤回）→ `idle`。后台节流标签页不给结论，快速连点不会发两次换肤请求。

### P2 — 结构性，本轮的真正答案

**实现 `docs/compat-profile-design.md`：签名的、可热更新的兼容档案。**

`GET https://api.dreamskin.cc/v1/compat/profile?platform=&client=&codex=`，返回签名的 selector + 白名单 CSS + readiness 阈值。
客户端启动时异步拉取、fail-closed 校验（签名 → schema → revision 单调 → 未过期 → minClient → key 必须已存在于内置合同）、
**只允许覆盖 `selector` 字符串**，不允许新增 key / 改 tier / 改 required——降级面因此有界，最坏等于「某个锚点选不中」。
硬边界：**档案是数据，不是代码**，绝不接受脚本、URL、文件路径、命令。

前置条件：运行时其实已经具备解耦能力——安装后的 injector 是运行时从磁盘读 `assets/selectors.json` 的，
只是没有第二个来源。

## 5. 环境与流程陷阱（踩过的，别再踩）

**本机能跑什么**（维护者是 macOS）：
- ✅ `node --test macos/tests/*.test.mjs windows/tests/*.test.mjs tools/*.test.mjs`（当前 124 项全绿）
- ✅ `node tools/sync-runtime-assets.mjs --check`、`node {macos,windows}/scripts/injector.mjs --check-payload`
- ✅ Swift typecheck：**必须用 MacOSX14.4 SDK**，15 SDK 对 Swift 5.10 CLT 太新，会在 stdlib 接口上报一堆假错：
  ```
  swiftc -emit-module -module-name DreamSkinCore -sdk $SDK -target x86_64-apple-macos13.0 \
    -emit-module-path $TMP/DreamSkinCore.swiftmodule macos/menubar-app/Sources/DreamSkinCore/*.swift
  swiftc -typecheck -sdk $SDK -target x86_64-apple-macos13.0 -I $TMP \
    macos/menubar-app/Sources/CodexDreamSkinMenuBar/*.swift
  ```
- ❌ **没有 `pwsh`**，`windows/tests/*.tests.ps1` 一次都跑不了，只能靠 CI 的 PowerShell 5.1 / 7 两个 job
- ❌ 没有完整 Xcode，跑不了 SwiftPM/XCTest
- ❌ 没有 Windows 主机

**合并机制**：`main` 有分支保护（`required_approving_review_count: 1`、`require_last_push_approval`、
`required_conversation_resolution`），`enforce_admins` 关着。
别人的 PR 可以 `gh pr review --approve` 后正常合；自己开的 PR GitHub 不允许自我 approve，只能 `--admin`，**先问过再用**。
外部贡献者的 CI 默认 `action_required`，要 `gh api -X POST repos/.../actions/runs/$RUN/approve` 放行。

**发版**：`release.yml` 在 push 到 `main` 时触发，但 guard 会 diff `macos/VERSION`，没变就不发。
版本号有**六处**必须一致（CI 的 `Check version consistency` 会卡）：
`macos/VERSION`、`windows/VERSION`、`macos/package.json`、`macos/scripts/common-macos.sh` 的 `SKIN_VERSION`、
两个 `injector.mjs` 的 `SKIN_VERSION`。

**网站部署**：Cloudflare Pages **没接 GitHub 自动部署**，push 不会发布。
```
cd apps/site && npx vite build
cd <仓库根>                        # wrangler 的路径参数相对 cwd，在 apps/site 里跑会 ENOENT
npx wrangler pages deploy apps/site/dist --project-name dreamskin-cc --branch main \
  --commit-hash "$(git rev-parse HEAD)" --commit-message "..."
```
`--branch main` 才是正式发布。自定义域名有 20–30 秒传播延迟。
`corepack pnpm <任何命令>` 会先触发 install 并要求清空 `node_modules`，无 TTY 直接失败；
绕过：`npx vite build` / `node --test src/lib/*.test.mjs` / `npx tsc -p apps/site/tsconfig.json`。

**跨仓**：commit message 里写 `Fixes #301` **不会**跨仓关闭 issue，必须
`gh issue close --repo Fei-Away/Codex-Dream-Skin <N>`。
